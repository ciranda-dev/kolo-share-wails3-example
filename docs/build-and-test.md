# Build and test

The repository has no `go.work` and no `replace`, so use `GOWORK=off` when this folder sits inside a Go workspace. The Kolo libraries are pure Go; only Wails needs cgo on macOS and Linux, for the native window. Besides Kolo and Wails, the example uses `golang.org/x/sys` (already in Wails' dependencies) to set the macOS quarantine attribute.

## Checks

```sh
GOWORK=off go vet ./...
GOWORK=off go test -p 1 ./...       # about two minutes; every test runs on 127.0.0.1 in temporary folders and none sends to a public address
GOWORK=off go test -race -p 1 ./...
cd frontend && npm test && npm run lint
```

What the tests cover:

- `session_test.go` runs two or three services in one process, without the window, on a private loopback network. `TestSessionFile` and `TestSessionFolder` pair two examples, send a file of 3 MiB and a folder with nested files, an empty folder, a link (not sent) and names that Windows refuses, and compare them byte for byte; nothing is in the folder before Save. Other tests cover both directions at once, decline, cancel by either side, a lying offer, a tampered chunk, a dropped connection (the session comes back and the receive continues by itself), offers resent after a reconnect, auto-save off by default and within the limits, goodbye on close and on quit, a peer that vanishes, a stranger on the session topic, and every pairing rule: single use, cancel, expiry, own code, the session limit, a new pairing with the same person and nothing on disk.
- The networks: `TestResolve`, `TestLoadConfigLocal` and `TestBootstrapFailure` check that no flag means the public list (nothing is sent), that `-bootstrap` is used alone, that `-local` runs on loopback, that `-local` with `-bootstrap` or `-first` is refused and what the unreachable public network says; `TestPublicModeSettings` holds the start so the public network is never contacted. Every other test passes `-local`, `-first` or `-bootstrap` to a loopback node, and `startPeer` fails a test that would reach the public network. The `TestLocalMode*` tests run the local network, and the session tests run on your own network.
- Hostile peers: `TestOfferLimits`, `TestOfferRate` and `TestMalformedControlEndsSession` play a peer that floods offers, offers huge sizes and names such as `../x`, and sends malformed control messages; `control_test.go` and its fuzz targets check the control frames, the pairing payload and the join data.
- `prep_test.go` covers the announcement of an item being prepared, on loopback: the receiver shows the card before the offer of a slow preparation (a hook holds the send at every chunk), the card turns into the offer with the same ID, its progress arrives and is throttled to two a second, a cancel, a failure and a silent sender end the card with their reasons, an item over the receiver's limits shows no card, an app of an earlier version never gets an announcement and keeps working, a message it cannot read ends its session as it did before, announcements are bounded by `maxOpenOffers` and by the rate, they survive a reconnect, and hostile frames end the session. `control_test.go` round-trips and fuzzes the new messages.
- `e2e_test.go` also runs two examples through an `internal/netsim` link shaped like the paths of a field test: a 1 KiB item over a 470 ms round trip is saved within 12 round trips (about 10: two logs, each a head, a header and a pull of three round trips), the progress moves within the first answer at 50 KB/s, a 200 KiB item over 2 KB/s says the path is slow and finishes (about 2 minutes, skipped with `-short`), packets capped at 1240 bytes from the start or at 1280 after a large transfer still carry 3 MiB (skipped with `-short`), and Cancel ends a transfer within 2 seconds on a slow path and on a path that carries nothing, from either card, or fails with the stack of every goroutine. `KOLO_SHARE_MTU_DROP=1` adds a cap of 1280 bytes after a large transfer: it passes with a kolo-transport that falls back to 1200-byte packets once the large ones are lost (in its CHANGELOG under Unreleased, so through the workspace `go.work`) and fails with kolo-transport v0.1.0, which keeps the larger size it found. `watch_test.go` checks that the bar stops at the total while the speed counts every byte, and that bytes that do not move the bar still end a stall.
- `resume_test.go` cuts the network (a test firewall on both examples plus a closed connection) in the middle of a 50 MB item for 10 seconds: the item says it waits, continues by itself, saves the same tree and fetches every entry once; Cancel works while it waits, and a sender that does not come back ends the receive after `-resume-for`.
- `store_test.go` covers the stores of large items: the 64 MiB threshold, at most 2 tuned stores at once, and that a store's place and folder are given back when its item is cancelled by either side, fails or is delivered. `bench_test.go` is skipped unless `KOLO_SHARE_BENCH=1`: `KOLO_SHARE_BENCH=1 GOWORK=off go test -run 'TestBench' -v .` prepares 1 GiB with the default and the tuned store, then sends and receives 1 GiB between two examples on loopback with each, and prints MB/s (it needs about 5 GiB of free disk in the temporary folder and takes a few minutes).
- `space_test.go` covers the disk checks and the sizes of items of 100 GB and 1 TiB: what a store needs, the room that running transfers hold per disk (two disks, one disk, a volume that cannot be asked, 20 reservations at once), the sentences, a send that fails before it stores a byte, a receive of a 100 GB offer declared in its metadata (refused with 50 GB free, taken with room and ended by the check of its tree), the default limit of 1 TiB and a 2 TiB offer declined with it. A hook (`freeSpace`, `volume`) plays the disk; the tests never fill a real one.
- `scale_test.go` builds a log of 150,000 entries with the real kolo-log and kolo-store code and pulls it over loopback with the example's `pullLog`: `go test -run ScaleLog -v` takes about 25 seconds with the sender's log in memory, and `KOLO_SHARE_SCALE_WRITER=pebble` puts it on Pebble too, which syncs at each append and takes about 11 minutes; `KOLO_SHARE_SCALE_ENTRIES` changes the count. It prints the time and the heap of the append, the head and its proofs, the pull and the check of every entry when the store is opened again.
- `copy_test.go` covers the parallel save: files around the size of a range, a file split into ranges at offsets above 2^32 (sparse, no disk), a read that fails in one range, a cancel, and a cancel during the copy of the last file, which leaves nothing in the folder; `store_later_test.go` covers the grouped commits (random operations against the plain backend, order, the bound of the queue, a failing disk, 8 goroutines with `-race`).
- `bigbench_test.go` is skipped unless `KOLO_SHARE_BIG=1`: `TestBenchBig` sends and receives one real file of `KOLO_SHARE_BIG_GIB` GiB (default 3, at most 12) between two examples in this process through a netsim link (`KOLO_SHARE_BIG_MBIT`, `KOLO_SHARE_BIG_RTT_MS`) and prints the speed of the prepare, the pull and the save, the peak heap, resident size and temporary disk, then checks the SHA-256 of the saved file; it needs about 3.5 times the size in free disk (a size over 3.4 GiB needs `KOLO_SHARE_BIG_ALLOW_DISK=1`, since a test may use 12 GiB), and `KOLO_SHARE_BIG_BASELINE=1` turns the grouped commits and the parallel save off for a before and after. `TestBenchManyFiles` does the same for a folder of up to 99,000 files.
- `transferlog_test.go` covers the `transfer:` log lines: the format of the receiver's and the sender's line (parsed), that a pull passes a meter and logs while it runs and once at the end, with the connection words of kolo-transport's `Conn.Stats` (format, a connection with no statistics, the sender's busiest of several connections, and, on a real loopback connection, that they are there; none needs a network), that `-quiet-transfers` drops the periodic lines, that a canceled or failed pull logs its end without the error text, and that no goroutine is left behind. A pull against a peer that predates streaming is not tested: kolo-sync's tests keep a frozen copy of that peer that this repository cannot import.
- `link_test.go` and `growth_test.go` cover the transport of the session swarm: its effective kolo-transport settings (growth on, 256 KiB start windows, the ceilings and the budget, BBR by default and each `-congestion` value, the memory under kolo-transport's default `MaxMemory`), that `Allow` admits only the key of an open session, that kolo-swarm marks only the paired peer for growth, and, through a delayed `internal/netsim` link, that the window of the paired peer's connection grows past 1 MiB under fast reading while a key that is not paired is refused. `TestCongestionSetting` covers the flag, the variable and the refusal of a bad value. `TestBenchLink` is skipped unless `KOLO_SHARE_BENCH=1`: it pulls `KOLO_SHARE_BENCH_MIB` MiB (default 100) between two examples over five simulated paths (round trip, rate and loss: 100 ms and 100 Mbit/s, 100 ms and 20 Mbit/s with 1 percent loss, 30 ms and 100 Mbit/s, 30 ms and 20 Mbit/s with 1 percent loss, 60 ms and 20 Mbit/s with 3 percent loss) with kolo-transport's defaults, with flat 4 MiB and 8 MiB windows and with the growth and BBR the example sets, and prints MB/s; `-run BenchLink/100ms_100Mbit_noloss/growth_bbr` picks one run.
- `hardening_test.go` and `notch_test.go` cover the safety rules: Reveal's argument vectors with hostile names, the file and log entry limits (before the pull, after it and in the plan), the `.part` name and the sweep after a crash, cleaned names, the downloaded mark, the hidden notch window, that the notch never gets a pairing code or a session secret, the notch and tray mapping of offers, the Linux tray guard and the data directory rules.
- `frontend/test/crash.test.mjs` opens both windows with the mock in a headless Google Chrome on 127.0.0.1 (skipped without Chrome): null lists leave no blank window, and an error in a render, an event or a promise shows the error pane, which fills the window, reaches `ReportError` and copies.
- `frontend/test/shell.test.mjs` opens the window with the mock in a headless Google Chrome (skipped without Chrome): the sidebar collapses and remembers it (and works without storage), the "+" menu and its two dialogs take the keyboard, trap the focus and give it back, the actions of a session are all reachable, the network line names no address, and a narrow window does not scroll sideways. `frontend/test/sidebar.test.mjs` checks the stored choice, the focus steps and the avatar colors.

The tests keep identities in memory and never write a key file.

## Builds

- `GOWORK=off wails3 build` builds `bin/kolo-share` for this computer.
- `GOWORK=off wails3 task windows:build ARCH=amd64` cross-builds `bin/kolo-share.exe` for Windows on x86-64 from macOS or Linux with no extra tools, since Wails on Windows needs no cgo. (`wails3 build GOOS=windows` builds for the host's architecture.)
- A Linux build needs cgo with GTK 4.10 or later and WebKitGTK 6.0 (Wails v3.0.0 does not build against GTK 4.8), so build it on Linux, for example Debian trixie or Ubuntu 24.04 with `libgtk-4-dev` and `libwebkitgtk-6.0-dev`.

## Release files

`scripts/release-local.sh [output dir]` builds the release files of the committed HEAD on a Mac, unsigned:

- macOS: a universal `.zip` and `.dmg`;
- Windows amd64 and arm64: `.exe`, `.zip` and installer;
- Linux amd64 and arm64: `.tar.gz` and `.deb`, built in Docker;
- `SHA256SUMS`.

It needs Go, Node.js, the `wails3` CLI and Docker.

The version is the git tag (`git describe --tags`). The script passes it to the example with `-ldflags "-X main.version=..."`, so Settings and `Info().version` show it, and `scripts/set-version.sh` writes it into the files that carry one: `build/config.yml`, the macOS `Info.plist`, the Windows manifest, `info.json`, the MSIX files, the NSIS defaults and `nfpm.yaml` (committed with the development version 0.0.0). The script checks that each Windows and Linux binary carries it. A build without `-ldflags`, such as `go build` or `wails3 dev`, reports `dev`; `wails3 task package` takes the version from the tag, or `APP_VERSION=0.1.0` on the command line.

The AppImage target downloads linuxdeploy at a pinned release and checks its SHA-256 before it runs it. The Windows uninstaller deletes the files the installer wrote and the folder only if it is empty, since the person may install into a folder that holds other files. The deb names Ciranda as its maintainer and https://kolo.ciranda.dev as its homepage.
